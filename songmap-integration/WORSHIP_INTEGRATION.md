# Worship integration — Debug experiment

This branch connects the validated palette6 pipeline to SongMap's real audio decoder and MusicUnderstanding boundaries. It is a draft: no iOS SDK build or app-level validation has been run here. Benchmark success does not validate app audio resampling, resource bundling, or overlap with other analysis stages.

## Install local models

From this SongMap checkout, use the prepared hybrid benchmark directory on your Mac:

```bash
python3 scripts/install_worship_benchmark.py
python3 scripts/generate_xcode_project.py
open SongMap.xcodeproj
```

By default the installer finds the latest prepared hybrid benchmark in the sibling `Section-Annotations/outputs.local` directory. Supply `--benchmark-dir /absolute/path/to/project` to override it.

The installer copies compiled models into the ignored `SongMap/Resources/MLModels/SongFormerWorship` folder. It preserves legacy assets. Compiled static and dynamic models duplicate weights, so this is a local integration experiment, not final production packaging. Do not commit binary assets from this installation. Confirm Xcode includes the ten `Worship_*.mlmodelc` resources and `songformer_worship_manifest.json` in the target; all must be present before testing.

In Xcode → Scheme → Run → Arguments, add `--songformer-worship`. This enables the worship path only in Debug, with CPU as the default. `--songformer-worship-cpu` explicitly keeps CPU mode. Experimental partial hybrid requires the additional `--songformer-worship-hybrid` argument, but is not the recommended retest path after runtime crashes. MusicFM 3000-frame GPU routing is disabled even with that opt-in because the app reported a fatal MPS reshape assertion. Release builds continue using the legacy path.

## Result contract

- MusicUnderstanding supplies boundaries; no new boundary detector is added.
- The head normalizes only IDs 0,1,2,3,4,5,6,26 before section pooling.
- Each output frame covers 0.12 seconds with the exact 420-second chunk offset.
- Pooling weights each frame by its overlap duration with the Apple section, including crossings of head chunks.
- The worship path preserves Apple ranges, repeated labels and silence. It bypasses legacy snapping, folding and majority voting. The grid/chart consequences require app review.
- CPU is the default for all components. In explicit experimental hybrid mode, eligible full windows use static `all` models, except MusicFM 3000 frames which is blocked due to a fatal GPU assertion. Partial windows use original-length CPU models.
- Catchable static inference errors and non-finite static outputs retry the same weights on CPU. OS termination and fatal GPU assertions cannot be caught. Use the CPU launch argument if the hybrid runtime is unstable.
- The new assets are required when the flag is set. Missing assets fail explicitly; the app does not silently use old encoder weights.

### Debug audit of MusicUnderstanding boundary consistency (2026-11-19)

The dataset boundaries come from `SongStruct-Models/apple/ExportBoundaries.swift` on the Mac: `[.structure]` alone on an `AVURLAsset` with `AVURLAssetPreferPreciseDurationAndTimingKey`. The app asks for `[.structure, .rhythm, .key, .instrumentActivity]` in one session on a default `AVURLAsset`. The imported file is a byte copy of the MP3, so the input is the same. On Raise a Hallelujah the app produced 26 sections (first starting at 1.4 s, one boundary at 6:45.1 instead of 6:48.1) against the export's 28; Alleluia matched exactly. The cause is not established: the call configuration, run-to-run variation and the iOS vs macOS model are all possible.

With the Debug launch argument `--musicunderstanding-boundary-audit`, the provider keeps using the app's own pass for the analysis and additionally records, in `boundaryAuditEvidence` of the analysis diagnostics, three extra MusicUnderstanding passes on the same file: structure-only with precise timing (the exporter's call), the same call again (run-to-run consistency), and structure-only with default timing (isolates the timing option). `scripts/compare_boundary_audit.py` matches each report to the Mac export by audio file name and reports, per configuration, section counts, one-to-one boundary F within 0.5 s and 3 s, mean shift, and a verdict: app call (fixable by calling like the exporter), run-to-run variation, or device (iOS vs macOS model; not fixable by the call). This measures consistency with the Mac export only; manual boundaries were locked during annotation, so boundary correctness itself cannot be scored without a corrected subset.

Result (iPhone18,1, iOS 27.0.1, Debug with the audit; dataset reference = the 28 / 19 original Mac intervals carried in the probe reports):

| Song | Configuration | Sections (Mac) | Boundary F@0.5 s | F@3 s | Mean shift |
|---|---|---|---|---|---|
| Raise a Hallelujah | app combined call, default timing | 26 (28) | 0.83 | 0.94 | 0.23 s |
| | structure only, precise timing (exporter) | 26 | 0.75 | 0.94 | 0.27 s |
| | same, repeated | 26 (identical) | 0.75 | 0.94 | 0.27 s |
| | structure only, default timing | 26 (identical) | 0.75 | 0.94 | 0.27 s |
| Alleluia | all four | 19 (19) | 1.00 | 1.00 | 0.01 s |

On the phone MusicUnderstanding is deterministic: repeated calls are identical, and the app's boundaries also equal the earlier in-app run. The timing option makes no difference. Calling it like the Mac exporter does not reproduce the Mac export and is slightly further from it than the app's combined call. The difference is therefore the iOS vs macOS analysis itself, which the app cannot change by its call; the app keeps its current call. Raise a Hallelujah differences: song start 1.37 s vs 2.71 s, 0:28.56 vs 0:29.91, 1:35.00 vs 1:30.74, 6:45.14 vs 6:48.08 (2.94 s, one bar at the song's 2.93-s bar), and no boundary at 5:55.40 (two sections merged). Which device is closer to the music cannot be scored without manually corrected boundaries.

### Release integration: MuQ-only labels in the "sections" asset pack (2026-11-19)

Decision: accept the iPhone MusicUnderstanding boundaries as they are (deterministic on the device, labels match the Mac reference on 23/24 sections) and ship the validated MuQ-only pipeline as the app's section labeler.

- Branch merged with `main` (asset packs, `ModelLocator`, AssetDownloader extension). The MuQ-only pipeline and the legacy analyzer resolve compiled models through `ModelLocator.modelURL(named:)`, so a model can come from the app (Debug) or from an asset pack (Release).
- `SongFormerAnalyzer`: Release always runs the MuQ-only pipeline (palette6 head + section context over Apple's boundaries, CPU only, no boundary refinement). Debug runs it too unless a launch option picks another path (`--songformer-legacy`, `--songformer-worship…`).
- New asset pack `sections` (`ModelPack.sections`) with `SongFormerMuQ_LogMel/Conv/Encoder/Head/Context.mlmodelc`. `ModelResource.songAnalysis` asks for `sections` and `lyrics`; the four-stream `structure` pack of Lyra 1.1 is no longer requested, and the AssetDownloader extension skips it, so new installs download only the MuQ models (compiled MuQ bank 184.5 MB instead of the MusicFM + MuQ encoders). Lyra 1.1 keeps reading its own `structure` pack, which is unchanged.
- The compiled models are tracked in Git LFS exactly as validated on the iPhone (`SongMap/Resources/MLModels/SongFormerMuQ/`, written by `scripts/install_muq_pipeline.py`); `songformer_muq_manifest.json` stays in the app. Release leaves the five `.mlmodelc` out of the app (`SONGMAP_ASSET_PACK_FILES`). `scripts/build_asset_packs.py --pack sections` packs them without recompiling and refuses any file whose SHA-256 differs from the manifest's `compiledFiles`.
- Analysis diagnostics reports are written to disk in Debug only.
- `scripts/tests/test_sections_asset_pack.py` keeps the pack builder, `ModelLocator`, the Release exclusion list, the installer and the downloader in step.

Before the TestFlight build from `main` can label sections, the `sections` pack must be built on the Mac and uploaded to App Store Connect (as for the `structure` and `lyrics` packs):
